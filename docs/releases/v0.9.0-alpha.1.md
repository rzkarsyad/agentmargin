# AgentMargin v0.9.0-alpha.1 — draft release notes

**PREPARED ONLY. No tag, GitHub Release, npm publication or production deployment.**
Platform target `v0.9.0-alpha.1`; additive SDK target `0.5.0-alpha.1` / tag
`sdk-v0.5.0-alpha.1`. Published SDK remains `0.4.0-alpha.2`.

The candidate adds credential-backed PostgreSQL tenant isolation; snapshot/catalog
containment; operational backup/metrics/readiness tooling; durable invoice/refund/
credit replay; append-only original payments, linked reductions and delivery audit;
and exact net revenue/known/unknown contribution with traceable reconciliation.
Current Stripe credit-note allocation schemas and platform routing are supported
within explicitly documented limits. Dashboard design and prior SDK methods remain.

Compatibility: PostgreSQL 16 is the tested target. Drain all writers, validate an
isolated restorable backup, apply only unapplied migrations in order through 014,
reapply restricted runtime grants, deploy matching API/worker/receiver, check
readiness and synthetic tenant/replay/report probes. Do not deploy intermediate
007–013 as the final security fix. READ COMMITTED is required. Old clients retain
ingestion APIs; newer methods need the matching server. Existing revenue analytics
fields now mean **net recorded revenue** after adjustments; explicit gross/refund/
credit/reversal fields explain it. Original records are never silently rewritten.
No destructive down-migration or grant broadening is a rollback strategy: roll
forward or restore into a new isolated environment with its matching source.

Known limits: no independent security/accounting sign-off; admitted cursor/in-flight
revocation window and shared ingest/inbox authority; unsupported FX/mixed or
prepayment credits/reinstatements/cache-creation tiers; genuine paid/refund/credit
sandbox and official billing-export validation incomplete. The observed genuine
unpaid test invoice does not establish an end-to-end financial integration.
Synthetic backup/browser/security tests do not certify production operation.

The [release dashboard](../ROADMAP.md) owns current PR/CI and gate evidence.
[Accounting](../ACCOUNTING_POLICY.md), [security](../TENANT_THREAT_MODEL.md),
[operations](../BACKUP_RESTORE.md) and [privacy](../PRIVACY_LIFECYCLE.md) describe
remaining restrictions. Report security concerns through SECURITY.md, not public
credential or financial exports.

After approvals and protected integration: rerun all CI/CodeQL on final main,
regenerate source/SDK archives and migration hashes from that commit, independently
review manifest/SHA256SUMS and clean-consumer output, and obtain explicit tag/
publication authorization. Then use the existing `publish-sdk.yml` Trusted Publisher
with the approved SDK alpha tag and npm-publish environment. No long-lived npm
publish token. Create the platform **prerelease** using these finalized notes and
reviewed artifacts only after authorization.

Post-publication: compare GitHub/npm versions and tarball digests, verify npm SLSA
provenance/signatures, run `node scripts/sdk-registry-consumer-smoke.mjs --version
0.5.0-alpha.1 --verify-signatures`, clean ESM/TypeScript/Next.js consumption and a
synthetic local upgrade. Record actual URLs/run IDs. If defective, stop promotion,
communicate known limitations and publish a separately authorized corrected alpha;
never overwrite npm versions, move reviewed tags or weaken grants. A source alpha
release is distinct from a production SaaS deployment.
